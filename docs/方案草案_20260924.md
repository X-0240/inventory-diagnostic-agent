# 方案草案：库存补货与调拨 Agent

版本 v3（2026-09-24）：经三轮另一个 AI 迭代 + 一轮独立审查 + 一轮短审确认（有条件通过，条件已满足）。第 10 节已由设计级扩写为字段级接口契约并**冻结**，实现不得违反；不另开契约文档。

v1 → v2 变更摘要：定位句改为「边界内诊断」；范围收缩（不做完整采购生命周期、退货、应付 AP、看板、账号平台）；表 17 → 13 张；采购单状态机去掉部分到货；`ranking` 改为 `proposed_actions` 且仅供审批参考；错误码由 9 个增至 16 个并新增「副作用状态」与「对账动作」两列；新增审批快照与执行前复检；新增评测集与调参集分离、多固定种子、敏感性分析；LangGraph 对照实验降级为最小崩溃恢复验证；指标分三档。

v2 → v2.1 修正三处（短审确认项）：崩溃恢复验证补关键注入点（采购单插入后、建议置 `EXECUTED` 前杀进程）；`case_id` 归属改到 `replenishment_suggestion`（原写在 `exception_case` 上，与「一个异常可有多个建议版本」方向相反）；`job_run` 补 `side_effect_status` 与 `reconcile_action`，为 `RESULT_UNKNOWN` 与对账任务提供落点。

v2.1 → v3：第 10 节扩写为可实现的字段级契约并冻结（13 张表逐列定义、状态迁移表、工具签名与返回、LLM 可用工具白名单、上下文 state 字段、变更规则）。

## 0 定位句与项目主张

定位句：用 LLM 做边界内诊断，用规则守数量，用审计证明边界。

项目主张（不得夸大）：本项目主张「边界内诊断可靠」，不主张「AI 会补货」。正常路径无 LLM 调用；LLM 只在异常 SKU 上做假设生成、证据收集与整理、是否需要人工介入的判断。所有业务效果数字一律标注为仿真结果，不作因果主张、不外推到真实业务。

## 1 为什么做

SKU 上千之后补货靠人工经验算不出来，结果是断货与超储同时存在。补货量有确定性公式，交给 LLM 等于引入不可复现、不可审计的误差，也会被追问「为什么不写公式」。所以数量计算锁在确定性函数里，LLM 只做工具编排、异常归因、例外处置与把依据讲成业务语言。

与主项目的区别：主项目的状态是对话状态（messages 列表，临时、可截断）；本项目的状态是业务状态（库存、在途、单据，持久、有流转约束、跨进程）。主项目只读，本项目有写操作闭环。

诚实边界：本项目不是生产系统，不声称解决企业实际补货问题；它复现真实流程，数据来源与构造方式一律如实标注。

## 2 已定结论（不推翻）

1. 补货量与调拨量由确定性计算给出（安全库存、(s,S) 策略、经济订货批量、调拨成本对比），不交给 LLM；LLM 只负责编排（选工具、定参数）、归因、例外处置、把依据讲成人话。
2. 术语不用「需求预测」，用「基线需求估算」或「补货建议」，避免被当成 ML 岗追问模型选型。
3. 金额上限、账期、库存上限这些规则不是 AI 的对手，而是写操作的护栏。
4. 混合架构：正常 SKU 走规则路径，异常 SKU（促销、新品、供应商延迟、销量突变）走 Agent 多步归因。
5. 第一期范围：单仓补货 + 单供应商维度；跨仓调拨放第二期。
6. v2 范围收缩：不做完整采购生命周期（无部分到货、无多批次收货、无退货闭环，只到「建单 → 审批 → 受控执行 → 一次收货关闭」）；不做应付 AP 模块（账期仅作护栏参数）；不做看板；不做账号平台（四种角色走配置，审计记录 actor）。退货、多批次收货、跨仓调拨同放第二期。

## 3 架构（五层）

| 层 | 实现方式 | 边界 |
|---|---|---|
| 数据层（MySQL） | 见接口约定的 13 张表 | 表的权威定义在接口约定 |
| 计算层（确定性纯函数） | 基线需求估算、安全库存、再订货点与目标库存、(s,S)、EOQ（受 MOQ 与包装倍数约束） | 可单测，输入输出全是数值，无 LLM |
| 编排层（LangGraph） | 数据就绪校验 → 基线估算 → 异常识别 → 异常时多步归因 → 建议生成 → 护栏校验 → 审批中断 → 执行 → 复算 → 审计 | 正常 SKU 走快步路径，异常 SKU 走调查路径 |
| 执行层（受控执行器） | 全系统唯一有权写采购单的模块 | 只收结构化写请求，不收自然语言 |
| 观测层 | 审计事件 + 每节点耗时与 token + 对照实验留档 | 指标口径集中定义，不允许各处自定义 |

## 4 主链

销量与库存数据 → Agent 编排基线需求估算工具 → 结合在途、安全库存、交期做多步分析 → 生成补货建议（含金额与依据）→ 执行前护栏校验（金额上限、供应商账期、库存上限）→ 人工审批 → 受控执行器写入采购单 → 一次收货关闭 → 复算指标。

## 5 输入输出

输入：定时任务或人工指定 SKU 集合；销量日序列、库存与已预留、在途与预计到货日、供应商交期/账期/MOQ、成本与售价、服务水平；审批决定（批准／驳回／改数量＋备注）。

输出：补货建议（数量、金额、依据引用）；采购单；指标；审计记录。

## 6 关键坑

1. 口径先写死：销量按发货日还是下单日、含税与否、退货是否回冲、在途是否计入可用库存。
2. 在途是承诺值不是事实：交期 = 承诺交期 + 历史偏差修正。
3. LLM 绝不输出数量：数量只能来自 `suggest_replenishment`；不一致时以工具为准并记审计。
4. 幂等键 = `sku_id + period + content_hash`，唯一索引兜底，重复提交返回原单。
5. 审批与执行之间有窗口：取待审批、推进状态、写执行标记必须在单条条件更新内完成并检查 rowcount。
6. 审批绑定内容哈希，建议变更则旧审批失效。
7. 失败不无限重试：重试 3 次后转人工；已产生外部副作用的失败不可回滚，只能走取消与反向单。
8. 成本边界：LLM 只处理异常 SKU，正常 SKU 零调用。
9. 复算是闭环终点：预期库存与实际库存必须能对上，对不上要能定位到单据。
10. 审批依据必须冻结并可复检：护栏参数与账期在审批时冻结快照，执行前复检；参数已变则拒绝执行并要求重新审批。
11. 结果未知时不得重试：外部调用超时后必须先把结果对账清楚（`RESULT_UNKNOWN`），盲目重试会造成二次下单。

## 7 数据来源与环境构造（已定＝甲）

公开真实销量 + 自造库存/在途/交期/账期，如实标注。

- 模拟器以 SKU-天为粒度，固定随机种子（对照实验用 3–5 个种子）。输入：公开销量序列（仅作需求信号）、初始库存、补货策略参数、交期分布与到货波动、账期。输出：每日库存流水、在途、采购历史。
- 参数在跑对照实验前冻结并写入文档（预注册），防止为了让指标好看而调参。
- 口径标注模板：销量＝公开数据集 X（N 个 SKU × M 天，时间范围）；库存／在途／交期／账期＝由脚本按参数 P 生成，构造人＝我；期望结论＝由规则推导，非抽样标注；对照＝规则-only 路径。此类指标统称「仿真 KPI」。
- 待办：动手前核对所选公开销量数据集的规模与许可（截至 v2 未联网核实）。

## 8 验证

1. 计算层单测：手算对照，边界含 σ=0、交期=0、MOQ 大于需求量、销量全 0。
2. 场景集与评测集分离：一部分场景用于开发与调参，另一部分 held-out 场景只在最后跑一次，防止用同一批场景既调参又评测。每条场景预注册期望结论，报「通过 X/N」，属构造性测试，不称准确率。
3. 幂等与并发：同一建议并发提交 N 次，采购单必须只有 1 张；记录条件更新拦截次数（应大于 0）。
4. 崩溃恢复（最小验证）：两个注入点必须都测。(a) 审批中断后杀进程——此时尚未写采购单，验证重启后能续跑或转人工；(b) **采购单已插入、建议尚未置 `EXECUTED` 时杀进程**——验证重启后只能识别或回填原采购单，不得新建第二张。另含「超时后结果未知」场景，验证先对账、不重试。
5. 规则路径 vs 混合路径对照：两组共享同一套冻结参数与模拟环境，配对比较，多种子 + 敏感性分析，只比较整个「异常处置包」，不归因于 LLM 通用能力。对外表述：「该对照在冻结参数下让规则路径与混合路径共享同一模拟环境，唯一变量是异常处置包；因此差异只归因于异常处置增量，不归因于 LLM 通用能力，也不外推到真实业务。」
6. LangGraph 取舍：不做完整双实现、不报代码行数（行数可操纵）。改为定性说明 + 自建版所需模块清单（自建需实现：状态持久化、恢复语义、重复副作用防护、中断与恢复原语、节点级观测），并承认「选 LangGraph 是工程效率选择，不是能力证明」；唯一的实测是第 4 条崩溃恢复。

## 9 六条验收标准对照

| 标准 | 落在哪个模块 | 怎么满足 | v2 说明 |
|---|---|---|---|
| 1 真实业务场景 | 整条主链 | 补货是真实零售流程；普通大模型无法单独实现（数量必须走公式） | 部分满足：销量为公开数据、库存等为构造，如实标注，不声称真实业务数据 |
| 2 完整后端工程体系 | 数据层 + API + 审计 | FastAPI 接口、MySQL 表与索引（含慢查询前后对照）、角色权限、审计事件表 | 设计满足，实施待验证 |
| 3 核心 Agent 能力 | 编排层 | 多步归因（随证据变化展开，含反证）、异常分界可审计评分、失败恢复与重试上限、例外转人工 | 正常路径无 LLM；对外称「异常调查工作流」，不称自主补货 Agent |
| 4 上下文工程 | 编排层 state | 每节点 state 字段显式定义；工具结果先结构化摘要；只给异常 SKU 带序列摘要；证据引用带版本 | 需在实现中证明裁剪与引用，而不只是声明 schema |
| 5 可观测评估 | 观测层 | 工程指标实测；仿真 KPI 标注；对照实验留档 | 分三档，见 10.6 |
| 6 人机协同 | 审批中断 + 护栏 | 金额/账期/库存上限护栏、超阈值强制人工、低置信强制人工、审批绑定哈希、审计留痕 | 待并发、权限、故障测试落地 |

## 10 接口约定

### 10.1 数据表（13 张，字段级）

统一约定：InnoDB + utf8mb4；主键统一 `id BIGINT UNSIGNED AUTO_INCREMENT`；金额 `DECIMAL(14,2)`、数量 `INT`、比率 `DECIMAL(6,3)`；时间列 `DATETIME`（库内 UTC，展示按 Asia/Shanghai）；业务表不做物理删除（生成器重置除外）。列名后 ★ 表示有索引或唯一约束。

**sku**：id★、sku_code VARCHAR(32) UNIQUE★、name VARCHAR(128)、category VARCHAR(64)、supplier_id★、unit_cost、price、lead_time_days INT、moq INT、pack_size INT、service_level DECIMAL(6,3) 默认 0.950、status ENUM('ACTIVE','INACTIVE')、created_at、updated_at；INDEX(supplier_id, status)。

**supplier**：id★、supplier_code VARCHAR(32) UNIQUE★、name VARCHAR(128)、lead_time_days INT、lead_time_sigma_days DECIMAL(6,2)（交期偏差修正用）、payment_terms_days INT、credit_limit DECIMAL(14,2)（0 表示不限）、status ENUM('ACTIVE','INACTIVE')。

**inventory_snapshot**：id★、sku_id★、warehouse_id VARCHAR(32)、snapshot_date DATE、qty_on_hand INT、qty_reserved INT、qty_inbound INT（冗余快照，权威值仍以 inbound_order 汇总为准）、version INT（乐观锁）、UNIQUE(sku_id, warehouse_id, snapshot_date)★。

**sales_daily**：id★、sku_id★、sale_date DATE、qty INT、source_flag ENUM('PUBLIC','SIMULATED')（来源标注）、UNIQUE(sku_id, sale_date)★。

**inbound_order**：id★、sku_id★、po_id BIGINT NULL FK→purchase_order.id、qty INT、expected_date DATE、actual_date DATE NULL、status ENUM('IN_TRANSIT','RECEIVED','CANCELLED')、created_at；INDEX(sku_id, status, expected_date)。

**policy_snapshot**：id★、sku_id★、period VARCHAR(10)（如 2026-W39）、method VARCHAR(32)、baseline_daily DECIMAL(14,3)、sigma DECIMAL(14,3)、sample_days INT、service_level DECIMAL(6,3)、z DECIMAL(6,3)、safety_qty INT、reorder_point INT、target_qty INT、rule_version VARCHAR(16)、computed_at；UNIQUE(sku_id, period, rule_version)★。

**exception_case**：id★、sku_id★、period VARCHAR(10)、status ENUM('OPEN','INVESTIGATING','DECIDED','CLOSED','MANUAL_TAKEOVER')、hypothesis_type ENUM(6 值) NULL、confidence DECIMAL(6,3) NULL、owner VARCHAR(64) NULL、version INT、created_at、updated_at；UNIQUE(sku_id, period)★。**不存 suggestion_id**（一对多由 `replenishment_suggestion.case_id` 表达）。

**replenishment_suggestion**：id★、sku_id★、period、case_id BIGINT NULL FK→exception_case.id、qty INT、amount、basis_json JSON（依据引用）、rule_trace_json JSON（走过的规则）、hypothesis_type ENUM(6 值) NULL、evidence_refs JSON NULL（写入后不可修改）、conflicting_evidence TINYINT(1)、proposed_actions JSON NULL（仅供审批参考）、confidence DECIMAL(6,3) NULL、content_hash CHAR(64)、status ENUM('DRAFT','PENDING_APPROVAL','APPROVED','EXECUTING','EXECUTED','CLOSED','REJECTED','EXECUTION_FAILED','MANUAL_TAKEOVER','SUPERSEDED')、version INT、immutable_after_approve TINYINT(1) 默认 1、active_flag TINYINT GENERATED ALWAYS AS (IF(status IN ('DRAFT','PENDING_APPROVAL','APPROVED','EXECUTING'),1,NULL)) STORED；UNIQUE(sku_id, period, content_hash)★、UNIQUE(sku_id, period, active_flag)★（同一 SKU 同周期只允许一条活跃建议）、INDEX(status, updated_at)★。

**approval_record**：id★、suggestion_id★ FK、decision ENUM('APPROVE','REJECT','MODIFY')、decided_by VARCHAR(64)、decided_role ENUM('BUYER','APPROVER','SUPERVISOR','ADMIN')、content_hash CHAR(64)、approval_snapshot_json JSON（审批时冻结的护栏与账期参数）、comment、decided_at；UNIQUE(suggestion_id, content_hash)★（同一版本只能审批一次）。

**purchase_order**：id★、po_no VARCHAR(32) UNIQUE★、suggestion_id★ FK、supplier_id★、sku_id★、qty INT、unit_price、total_amount、status ENUM('DRAFT','SUBMITTED','CONFIRMED','RECEIVED','CLOSED','CANCELLED')、idempotency_key VARCHAR(96) UNIQUE★、approval_snapshot_json JSON、reverse_of_po_id BIGINT NULL（反向单指向原单）、created_at、submitted_at、confirmed_at、received_at、closed_at；INDEX(supplier_id, status)。

**audit_event**（不可变，只允许 INSERT，不授予 UPDATE/DELETE）：id★、entity VARCHAR(32)、entity_id BIGINT、event_type VARCHAR(48)、actor VARCHAR(64)、actor_role VARCHAR(16)、payload_json JSON、created_at；INDEX(entity, entity_id, created_at)★。

**job_run**：id★、job_name VARCHAR(48)、period VARCHAR(10)、status ENUM('RUNNING','SUCCEEDED','FAILED','DEAD_LETTER')、retry_count INT、next_retry_at DATETIME NULL、last_error VARCHAR(255)、error_code VARCHAR(32)、dead_letter TINYINT(1)、side_effect_status ENUM('NONE','POSSIBLE','CONFIRMED')、reconcile_action VARCHAR(64) NULL、started_at、finished_at、stats_json JSON；UNIQUE(job_name, period)★（兼作 job_lock，防同一周期重复跑）、INDEX(status, next_retry_at)★。

**config_version**：id★、config_key VARCHAR(48)、rule_version VARCHAR(16)、params_json JSON、frozen_at DATETIME、frozen_by VARCHAR(64)、note VARCHAR(255)；UNIQUE(config_key, rule_version)★。

已固定的口径（写死在实现里，不得各处再解释）：
- 可用库存 = `qty_on_hand − qty_reserved`，**不含在途**；在途只从 `inbound_order` 汇总。
- 销量口径：`sale_date` 为发货日，金额含税，一期不做退货回冲。
- 计划周期 `period` 用 ISO 周（如 `2026-W39`）。
- 保留 `config_version` 的理由：审查要求参数冻结与预注册，没有它无法证明参数确实被冻结过。
- v1 → v2 的砍法（已生效）：`purchase_order_line` 并入 `purchase_order`；无 `metric_snapshot`、无 `retry_task`、无 `user`；不建 case↔suggestion 关联表。

### 10.2 状态机与合法迁移

建议单（replenishment_suggestion）：

| 当前 | 允许的下一状态 | 触发者 | 守卫条件 |
|---|---|---|---|
| DRAFT | PENDING_APPROVAL | 编排 | 护栏校验通过且金额 > 0 |
| DRAFT | MANUAL_TAKEOVER | 编排 | 护栏不通过或 needs_human |
| PENDING_APPROVAL | APPROVED | 审批人／主管 | decision=APPROVE、角色金额权限匹配、content_hash 一致 |
| PENDING_APPROVAL | REJECTED | 审批人／主管 | decision=REJECT |
| APPROVED | EXECUTING | 执行器 | 单条条件更新（status='APPROVED' AND content_hash=?）且执行前护栏复检通过 |
| EXECUTING | EXECUTED | 执行器 | 采购单插入成功（与状态推进同一事务） |
| EXECUTING | EXECUTION_FAILED | 执行器 | 失败且副作用状态为 `NONE` |
| EXECUTED | CLOSED | 系统 | 收货事件到达 |
| EXECUTION_FAILED | MANUAL_TAKEOVER | 编排 | 仅当副作用为 `NONE` |
| 任一活跃态 | SUPERSEDED | 编排 | 生成新版本（旧版本保留，不可删） |

采购单（purchase_order）：`DRAFT → SUBMITTED → CONFIRMED → RECEIVED → CLOSED`；`DRAFT/SUBMITTED/CONFIRMED` 可转 `CANCELLED`（未收货且未产生外部副作用）；已 `RECEIVED` 不可取消，只能下反向单（`reverse_of_po_id` 指向原单）。部分到货与多批次收货为第二期，故无 `PARTIALLY_RECEIVED`。

异常案件（exception_case）：`OPEN → INVESTIGATING → DECIDED → CLOSED`；`OPEN/INVESTIGATING → MANUAL_TAKEOVER`；`MANUAL_TAKEOVER` 不是终态，必须填 `owner` 才能闭合。

任务（job_run）：`RUNNING → SUCCEEDED | FAILED | DEAD_LETTER`；`FAILED → RUNNING`（retry_count+1，不超上限）；超上限转 `DEAD_LETTER` 并落 `reconcile_action`。

全局规则：每个写操作只允许从唯一一个前置状态触发；`APPROVED` 后建议内容不可变（`immutable_after_approve`）。

### 10.3 工具签名与输出 schema

**LLM 白名单（只读与计算，允许调用）**

| 工具 | 入参 | 返回 | 可能错误码 |
|---|---|---|---|
| get_inventory | sku_id, warehouse_id | qty_on_hand, qty_reserved, qty_available, snapshot_date, version | NOT_FOUND, STALE_DATA |
| get_inbound | sku_id | [{po_id, qty, expected_date, status}] | NOT_FOUND |
| get_sales_series | sku_id, days | dates[], qty[], missing_days[] | NOT_FOUND |
| get_supplier | supplier_id | lead_time_days, lead_time_sigma_days, payment_terms_days, moq, credit_limit | NOT_FOUND |
| compute_baseline | sku_id, days, method | baseline_daily, sigma, sample_days, method | STALE_DATA, INTERNAL_ERROR |
| compute_policy | sku_id, service_level | z, safety_qty, reorder_point, target_qty, rule_version | NOT_FOUND, INTERNAL_ERROR |

**LLM 白名单之外（编排层或执行器调用；LLM 调用一律 AUTH_FAILED 并记审计）**

| 工具 | 入参 | 返回 | 可能错误码 |
|---|---|---|---|
| suggest_replenishment | sku_id, period | suggestion_id, qty, amount, basis[], rule_trace[], content_hash | RULE_VIOLATION, STALE_DATA, VERSION_CONFLICT |
| validate_guardrails | suggestion_id | ok, violations[{code, limit, actual}] | NOT_FOUND（不通过时返回 RULE_VIOLATION） |
| submit_purchase_order | suggestion_id, idempotency_key | po_no, status | STATE_CONFLICT, APPROVAL_INVALIDATED, AUTH_REVOKED, RESULT_UNKNOWN, PARTIAL_BATCH_FAILURE（重复提交返回结果码 IDEMPOTENT_REPLAY） |
| recompute_metrics | period | period, stockout_rate, turnover_days, excess_amount, sample_size, definition_version | INTERNAL_ERROR |

LLM 输出 schema 必填：`hypothesis_type`（枚举）、`evidence_refs`（列表，含 tool／参数／返回值摘要／时间戳，写入后不可修改）、`conflicting_evidence`、`proposed_actions`、`needs_human`、`confidence`。

`proposed_actions` 的语义（v2 修正，消除与「策略表决定恢复动作」的矛盾）：它是给审批人看的建议清单，每项 action 取自枚举 ADVANCE／SPLIT／REPLAN／HUMAN 并附 rationale，不驱动执行；重试、降级、转人工的实际动作由确定性策略表决定。枚举外输出一律拒绝执行（`SCHEMA_INVALID`）。

假设类型枚举：`PROMOTION_SURGE`、`NEW_PRODUCT_NO_HISTORY`、`SUPPLIER_DELAY`、`STOCKOUT_CASCADE`、`DEMAND_SHIFT`、`DATA_ANOMALY`。

`confidence` 的四项用途（都不自动放行）：异常调查优先级、人工复核级别（低置信强制人工，高置信仍需审批）、告警阈值、对照实验的校准观察。必须记录它与人工驳回结果的对应关系，只呈现对照表，不宣称校准良好。

### 10.4 错误码与结果码

结果码（非异常，不计入失败率）：`IDEMPOTENT_REPLAY`（幂等键命中，返回原结果，算成功）、`MANUAL_REQUIRED`（控制流转人工）。

| 错误码 | 触发 | 可重试 | 上限 | 副作用状态 | 对账动作 | retry | audit | 责任方 |
|---|---|---|---|---|---|---|---|---|
| NOT_FOUND | 资源或配置不存在 | 否 | 0 | 无 | 无 | 否 | 是 | 人／编排 |
| STALE_DATA | 快照过期或版本落后 | 是 | 3 | 无 | 无 | 是 | 是 | 编排 |
| RULE_VIOLATION | 护栏规则被违反 | 否 | 0 | 无 | 无 | 否 | 是 | 人 |
| STATE_CONFLICT | rowcount=0 或锁超时 | 是 | 1 | 无 | 重取状态后重判 | 是 | 是 | 编排／执行器 |
| RESULT_UNKNOWN | 超时后结果未知、副作用不明 | 否 | 0 | 可能已发生 | 先查外部结果／核对单据，禁止直接重试 | 是（作为对账任务） | 是 | 编排／人 |
| EXTERNAL_ALREADY_CONFIRMED | 外部已确认，禁止自动重试 | 否 | 0 | 已发生 | 按已确认结果核对并回填 | 否 | 是 | 人／编排 |
| PARTIAL_BATCH_FAILURE | 批量提交部分失败 | 有限 | 1 | 部分已发生 | 逐项核对成功清单，成功项不重做 | 是 | 是 | 编排 |
| UPSTREAM_TIMEOUT | 外部调用超时（可判定为未发生） | 是 | 3 | 无 | 无 | 是 | 是 | 编排 |
| RATE_LIMITED | 限流或配额耗尽 | 是 | 3 | 无 | 无 | 是 | 是 | 编排 |
| SCHEMA_INVALID | LLM 输出枚举外或 schema 不合法 | 有限 | 1 | 无 | 无 | 是 | 是 | 编排 |
| VERSION_CONFLICT | 版本或 hash 冲突 | 是 | 1 | 无 | 重取最新版本后重算 | 是 | 是 | 编排 |
| APPROVAL_INVALIDATED | 审批失效（建议版本变化或参数变更） | 否 | 0 | 无 | 退回重新审批 | 否 | 是 | 人 |
| AUTH_FAILED | 认证或权限校验失败 | 否 | 0 | 无 | 无 | 否 | 是 | 人／管理员 |
| AUTH_REVOKED | 权限被撤销（审批中或执行前） | 否 | 0 | 无 | 停止并通知管理员 | 否 | 是 | 人／管理员 |
| PERIOD_CLOSED | 跨周期截止，期间已关闭 | 否 | 0 | 无 | 转下期或人工开启 | 否 | 是 | 人 |
| INTERNAL_ERROR | 未分类异常 | 有限 | 1 | 无 | 无 | 是 | 是 | 编排 |

### 10.5 审批权限矩阵

| 角色 | 可提交 | 可审批 | 边界 |
|---|---|---|---|
| 采购员 | 是 | 否 | 不能批准自己提交的建议 |
| 审批人 | 否 | 是 | 仅金额 ≤ 阈值 |
| 供应链主管 | 否 | 是 | 金额 > 阈值 |
| 管理员 | 否 | 否 | 只配置参数，不参与审批 |

附加规则：提交人 ≠ 审批人；同 SKU 同周期重复提交被拒；审批记录存 actor + role + content_hash；审批时冻结护栏与账期快照（`approval_snapshot_json`），执行前复检比对。

### 10.6 指标口径（分三档）

第一档·工程可信（实测，可直接引用）：单元测试通过数；慢查询优化前后对照（执行时间／EXPLAIN 扫描行数／逻辑读页数）；单次建议的 token 与耗时；并发提交同一建议时采购单数量（应为 1）；杀进程恢复后是否重复下单；状态冲突拦截次数。

第二档·仿真 KPI（必须标注为仿真结果，不作因果主张）：缺货率＝有需求且库存为 0 的 SKU-天／有需求的 SKU-天；周转天数＝平均库存／日均销量（是否含在途写死）；超储金额＝Σmax(库存−目标库存,0)×单位成本。口径：模拟环境 + 参数 P + 种子 S + 对照为规则-only 路径 + 构造人＝我。

第三档·降级为清单（不报百分比或统计量）：预注册场景的通过与失败清单；`needs_human` 判断的场景级结果；`confidence` 与人工驳回结果的对应表。单人小样本不作为统计结论。

每个数字附：数据来源、样本量、时间范围、对照、判定人。

### 10.7 幂等与回滚

幂等键 `sku_id + period + content_hash`；反向单幂等键为 `original_po_id + reverse`（多次或分行需再加序号），不得复用原单键。
回滚：采购单未确认前可撤销（转 `CANCELLED` 并留痕）；已确认或已产生外部副作用的，只能下反向单，反向单必须独立审批并带自己的幂等键；`EXECUTION_FAILED → MANUAL_TAKEOVER` 仅适用于尚未产生外部副作用的失败；`RESULT_UNKNOWN` 先对账再决定。
执行侧保证：唯一约束 + 原子条件更新 + rowcount 判定；执行器是唯一写入方。
LLM 与执行器都不拥有删除能力。

### 10.8 上下文工程约定（LangGraph state 字段）

图状态是一组显式字段，每个字段写明由哪个节点写入、哪些节点只读：

| 字段 | 内容 | 写入方 |
|---|---|---|
| sku_id / period / warehouse_id | 本次处理的标识 | 入口 |
| facts | inventory、inbound[]、supplier、sales_summary{baseline_daily, sigma, sample_days, missing_days} | 基线估算节点 |
| policy | rule_version、safety_qty、reorder_point、target_qty | 策略节点 |
| anomaly | score、reasons[]、is_anomaly、quota_rank | 异常识别节点 |
| diagnosis | hypothesis_type、evidence_refs[]、conflicting_evidence、confidence、needs_human、proposed_actions[] | 归因节点（仅异常 SKU） |
| suggestion | suggestion_id、qty、amount、content_hash、status | 建议节点（数量只写工具返回值） |
| guardrails | ok、violations[] | 护栏节点 |
| approval | decision、decided_by、decided_role、approval_snapshot | 审批中断恢复后 |
| execution | po_no、side_effect_status、reconcile_action | 执行节点 |
| errors | [{code, at, node, retry_count}] | 任意节点 |

裁剪与引用规则：工具结果只以结构化摘要进上下文（销量序列按窗口摘要，不整段塞入）；正常 SKU 不进入归因节点，因此不带序列摘要；`evidence_refs` 一旦写入，后续节点只能读，不得改写。

### 10.9 冻结与变更规则

本节（第 10 节）在 v3 冻结，实现不得违反。如需变更：必须升版本号、在本文档记录变更理由与影响面、并说明它服务于哪条验收标准或哪个错误码。表结构变更一律走迁移脚本，禁止手工改库。
