# 载体边界（一期，选项 1）：Agent 只读上游

日期：2026-09-26 ｜ 版本：v1.5 ｜ 状态：已实现并实测

## 一、为什么加这一层

最容易被追问的一句是「你这个系统依附在什么业务上」。补货决策本身不是业务闭环：
销量、库存、在途这三类事实**不归补货系统所有**，它们属于电商/零售平台侧。
所以补一个载体服务 `commerce-core`，把「事实从哪来」变成一条真实的边界。

真实业务（选项 2）里，采购单的权威在上游 ERP——中大型公司的补货系统必须调 ERP 接口建单。
**一期不做选项 2**，只做选项 1：上游只读，采购单、审批、建议、审计仍写在自己的域内。
理由与代价写在方案草案「取舍 6」：一期要讲透的是**单库内的状态机约束、并发与崩溃恢复**；
同时引入跨系统写，就要处理建单超时但上游已提交、上游成功而本地记账失败、上游单被取消
这一串一致性问题，很可能两头都薄。二期再补幂等键跨系统传递、超时回查与定期对账。

## 二、边界怎么落地的（三件事）

1. **独立库**：载体用 `commerce` 库，Agent 用 `inventory` 库，两张库不共享账号。
2. **独立账号**：载体用自己的服务账号 `commerce_svc`（只对 `commerce.*` 有权限）；
   Agent 的账号 `inv_app` 对 `commerce` 库**没有任何权限**——这条有负向测试守着，不是口头边界。
3. **唯一入口是 HTTP**：Agent 侧 `src/inv_agent/facts.py` 提供事实源适配器，
   `OMS_MODE=table` 直读本地库（默认，演示与单测），`OMS_MODE=http` 调载体接口。
   两种模式返回**同一份行结构**，切换数据源不改业务逻辑。

## 三、接口清单（5 个）

| 接口 | 用途 | 关键点 |
| --- | --- | --- |
| `GET /products` | 商品与参数（交期、账期、起订量、包装倍数、服务水平） | 参数以上游为准，本地只提供身份（FK 用的 id） |
| `GET /products/{sku}/inventory` | 库存快照 | 口径与库内一致：可用＝在手−预留，不含在途 |
| `GET /products/{sku}/inbound` | 在途与交期内到货量 | `until` 过滤出「交期内能到」的部分 |
| `GET /products/{sku}/sales` | 销量序列 | 只作需求信号，基线与离散度由 Agent 侧算 |
| `POST /receipts` | 收货确认（载体自己的写） | 幂等键唯一 + 收货量不得超在途；三张表同一事务 |

附一个 `GET /products/{sku}/leadtime-bias`：已收货批次的到货偏差，给交期修正用。
鉴权用请求头 `X-Api-Token`；错误语义对齐 Agent 侧错误码（401→AUTH_FAILED、404→NOT_FOUND、
422→SCHEMA_INVALID、超时由调用方判成 UPSTREAM_TIMEOUT）。

## 四、实测证据

### 1. 换数据源不改结论（最强的一条）
同一批 SKU、同一周期、同一套参数与代码，**唯一变量是事实源**：

| 范围 | 结果 |
| --- | --- |
| 全量 200 个 SKU，周期 2011-W31 | 数量、金额、内容哈希 **200/200 完全一致**，0 个异常 |
| 冒烟子集 20 个 SKU，周期 2011-W30 | 20/20 一致（已固化为用例） |

口径：调用 `pipeline.evaluate`，比较 (qty, amount, content_hash) 三元组；判定人＝断言脚本。
`tests/test_commerce_boundary.py::test_table_and_http_give_same_plan` 每次跑测试都会复核。

### 2. 主链在载体模式下能整轮跑通
`OMS_MODE=http` 跑 `plan-period --period 2011-W31 --force --workers 4`：
200 个 SKU、109 个候选、按配额选 20 个进诊断、生成 166 条建议、0 个错误，
墙钟 18.4 秒（含进程启动；同口径下桩模式批量约 11–15 秒）。
口径：本机 Docker 单实例 MySQL + 本机载体进程，桩模式（无模型等待）。

### 3. 故障注入：上游挂了必须"响"，不能"静默成功"
构造用例（`_DeadTransport` 强制连接失败）：

- 单个 SKU 评估 → `PlanError(code=UPSTREAM_TIMEOUT)`，不是 NOT_FOUND（**不可用 ≠ 没数据**，处置不同）。
- 载体的商品清单都拉不到 → 批量任务判 `FAILED`、`job_run.error_code=UPSTREAM_TIMEOUT`、
  写 `PERIOD_PLAN_FAILED` 审计，且不把 `job_lock` 悬在 RUNNING。
- 口径：构造性用例通过数，不是统计指标。判定人＝断言脚本。

改这条之前这里有个真 bug：`list_products` 在 try 之外，上游挂掉会直接抛出去，
任务行永远停在 RUNNING、周期被锁死。测试先红后绿。

### 4. 账号隔离（负向用例）
用 Agent 账号执行 `SELECT ... FROM commerce.product` → 权限错误（`pymysql.err.MySQLError`）。
`tests/test_commerce_boundary.py::test_agent_account_cannot_read_carrier_db` 固定这条。

### 5. 收货：幂等 + 越界拒绝
同一幂等键提交两次 → 第二次返回原流水（`replayed=true`），库存只加一次、在途只清一次；
收货量 41 > 在途 40 → 409 `QTY_OUT_OF_RANGE`。
口径：构造用例断言。

### 6. 投影性能：逐行 INSERT → 批量提交
把本地生成结果投影到载体库（约 5.6 万行销量 + 2 千多行库存）：

| 写法 | 耗时 |
| --- | --- |
| 逐行 `execute`（跑了 7.5 分钟没跑完，手动终止） | >450 秒 |
| `executemany` 批量提交 | **5.4 秒** |

口径：本机到 Docker MySQL 的墙钟时间，同一批数据、同一个脚本。
和 v1.3「连接复用」是同一类教训：批量写入的成本大部分在往返，不在 SQL 本身。

## 五、一期已知边界（要主动说明）

1. **载体是本地模拟的上游**：数据由 `scripts/project_to_commerce.py` 从同一份模拟结果投影过去，
   所以两库同源、口径一致。换成真上游只换 `COMMERCE_BASE_URL`，接口契约不变。
2. **复算（缺货率、周转天数、超储金额）仍读本地投影**，没有走载体接口。
   二期做法是把聚合口径做成载体接口；现在这样不产生口径漂移（两库同源），但边界上要承认。
3. **商品主数据是本地引用行 + 上游参数覆盖**：本地 `sku` 行提供外键身份，参数以上游为准；
   载体有、本地没有引用行时会记 `NOT_FOUND` 到批量错误里，不静默丢弃。
4. **没有做的事**：跨系统写、超时回查、定期对账、部分收货、退货（都在二期）。

## 六、怎么复现

```powershell
# 1. 建载体库与账号（幂等）
.venv\Scripts\python.exe scripts\migrate_commerce.py
# 2. 把本地生成的事实投影进载体库
.venv\Scripts\python.exe scripts\project_to_commerce.py
# 3. 起载体服务
$env:PYTHONPATH="src"; .venv\Scripts\python.exe -m uvicorn commerce_core.api:app --port 8001
# 4. 以载体模式跑一轮
$env:OMS_MODE="http"; .venv\Scripts\python.exe -m inv_agent.cli plan-period --period 2011-W31 --force --workers 4
# 5. 边界用例
$env:PYTHONPATH="src"; .venv\Scripts\python.exe -m pytest tests/test_commerce_boundary.py -q
```

## 七、载体暴露出的单价绑定漏洞（v1.6 修复）

**问题**：建议金额是用事实源返回的单价算的，执行器写采购单时却读**本地** `sku.unit_cost`。
演示数据是同源投影，两边永远相等，所以一开始测不出来；接真上游后上游一调价，
就会变成"批的是 A 价、落的是 B 价"，而且没有校验收得住。

**修法（四步，缺一不可）**：
1. 建议金额与 `content_hash` 绑定事实源单价（`pipeline.evaluate`）；
2. 单价落库到 `replenishment_suggestion.unit_price`（迁移 `003_suggestion_unit_price.sql`）；
3. 审批快照冻结单价、数量、金额（`guardrails.freeze_approval_snapshot`），
   两条审批路径（图节点与按 ID 审批）共用同一个冻结函数；
4. 执行器只认快照里的单价与金额，并在执行前复检当前事实源单价，
   不一致或快照金额与建议金额不符 → `APPROVAL_INVALIDATED` + 审计。

**对照证据（构造性用例，同一份数据）**：

| 口径 | 计算 | 与审批金额 |
| --- | --- | --- |
| 旧：读本地 `sku.unit_cost` | 999.00 × 10 = 9990.00 | 与审批金额 1000.00 **自相矛盾** |
| 新：读审批快照 | 100.00 × 10 = 1000.00 | 一致 |

用例固化在 `tests/test_price_binding.py`（4 条）：落库单价必须等于快照单价（本地表仍然是 999，
证明它没读本地）、单价漂移必须拒执行且不留采购单、载体接口返回调价后同样拒执行、
单价变了内容哈希必须变。口径：构造用例断言，判定人＝断言脚本。
