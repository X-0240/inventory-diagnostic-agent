# 批量事实接口与数据版本（v1.7）

日期：2026-09-26 ｜ 版本：v1.7 ｜ 状态：已实现并实测

## 一、这一版只加两件事

按裁定，载体只补到"上游事实服务可信、可批量取数、可判断数据新旧"，
**不加**上游建采购单、库存调整、退货、对账、应付——那些会进入跨系统写一致性，冲淡主线。

1. **批量事实接口** `GET /facts`：一次传 SKU 列表，返回商品参数、库存快照、在途、近期销量、
   交期偏差；解决原来每 SKU 4–5 次接口的 N+1。
2. **数据版本字段**：商品与在途带 `data_version`、库存带 `version`，三者都有 `updated_at`；
   接口支持 `If-None-Match` 与 `updated_since`，Agent 能判断拿到的是不是最新。

没有新增任何状态机：接口是只读的，Agent 侧的写入路径一行没动。

## 二、接口规格

```
GET /facts?skus=A,B,C&warehouse_id=WH1&end=2011-05-15&days=56[&updated_since=...]
Header: X-Api-Token、可选 If-None-Match
```

返回：`{generated_at, warehouse_id, end, days, etag, items[], skipped[], unchanged[]}`，
每个 item 是 `{sku_code, product, inventory, inbound[], sales[], leadtime_bias[],
versions{product,inventory,inbound}, updated_at}`。

几个刻意的设计：

- **单次上限 200 个 SKU**，超了返回 422 `SCHEMA_INVALID`，让调用方分批；Agent 侧会自动按 200 分批。
  真实平台接口都有上限，这里不假装能一次要一千个。
- **内部固定 5 条查询**（商品、库存、在途、销量、交期偏差），全部按 SKU 列表批量取，
  用窗口函数 `ROW_NUMBER()` 取"每个 SKU 的最新一条 / 最近 N 条"，接口内部不会退化成 N+1。
- **在途版本单独按 SKU 取**：收完货的批次会离开在途列表，如果只对在途行取版本，收完货版本反而会"消失"。
- **查不到的 SKU 进 `skipped`**，不塞空对象，不静默丢弃。
- 整批指纹 `etag` 由每个 SKU 的三类版本加行数拼出来：任一 SKU 任一版本变了，指纹必变。

## 三、实测证据

### 1. 调用次数与耗时（全量 200 个 SKU，同一批数据、同一台机器）

| 取数方式 | HTTP 调用 | 墙钟 |
| --- | --- | --- |
| 逐个 SKU 取（v1.6 的行为） | **1000** | 8.1 秒 |
| 批量取（v1.7） | **1** | 0.8 秒 |
| 差异 | −99.9% | **10.0×** |

口径：`facts.HttpFactsSource.fetch_stats` 自己计数；桩模式（无模型等待），本机 Docker 单实例 MySQL
与本机载体进程；200 个 SKU 全部评估成功（200/200）。代码里把这个计数进了任务统计
`job_run.stats_json.source_calls`，以后每轮都能看到实际打了几次上游。

**真实整轮跑一遍**（`plan-period --period 2011-W21 --force --workers 4`，`OMS_MODE=http`）：
200 个 SKU、101 个候选、154 条建议（都是幂等重放，条数不变）、0 个错误；
任务统计里的上游调用是 **2 次**（1 次批量 + 1 次回退）。回退是设计内的行为——
批量缓存没覆盖到的 SKU 会自己回退到逐 SKU 接口，不做"缓存不全就报错"的假设。

### 2. 换批量不改结论

同一批 20 个 SKU、同一周期：逐个取数 vs 批量取数，数量、金额、内容哈希**完全一致**
（判定人＝断言脚本）。道理和 v1.5 的"换数据源不改结论"是一条：批量只是取数方式，
不进任何计算。

### 3. 版本字段真的能判断新旧

- `If-None-Match`：带上次的 ETag 再问一次，上游回 **304**，Agent 直接复用缓存（用例里把缓存
  TTL 手动拨过期，仍只回 304、缓存内容不变）。
- `updated_since`：只回在那之后变过的 SKU，没变的进 `unchanged`；过滤不改变整批指纹。
- **上游写操作会抬版本**：对同一 SKU 做一次收货确认，库存 `version` 与在途 `data_version`
  都变大、整批 `etag` 变化——这就是"Agent 能识别事实被上游改动"的实测形态。

## 四、Agent 侧怎么用

- `facts.HttpFactsSource.prefetch()`：按（仓、截止日、天数、SKU 列表）做请求指纹，
  TTL 内直接复用；过了 TTL 先带 `If-None-Match` 问一次，304 就继续用旧数据。
- 批量命中的 SKU 走缓存，没命中的自动回退到逐 SKU 接口——**不做"缓存不全就返回错"的假设**。
- 每条建议的 `basis` 里写进事实版本（`facts_version` 条目），所以一条建议能追到"当时用的是哪一版上游数据"。
- 表模式（`OMS_MODE=table`）不参与这些：`prefetch` 是空操作、版本返回空，行为与 v1.6 完全一致。

## 五、已知边界

1. **一期的版本递增只能靠载体自己的收货写**：数据由 `scripts/project_to_commerce.py` 重灌，
   所以 `data_version` 默认都是 1、`updated_at` 反映的是投影时间。接真上游后由上游维护版本。
2. 批量接口是只读的，不解决跨系统写；上游建单、库存调整、退货、对账、应付都没做（按裁定）。
3. 缓存是**进程内**的，多进程部署时各自一份；换成共享缓存（Redis）属于二期。
4. `days` 上限 730、单次 SKU 上限 200 都是设定值，不是行业实测。
5. 整轮跑下来是 2 次调用而不是 1 次：多出来的那次就是上面说的回退，属于设计内行为，不是漏取。
